# GEM — GymElite Manager

Full-stack multi-tenant gym management system. Built for Cameroon-based gyms (currency: XAF/FCFA).

## Tech Stack

- **Frontend:** React 18 + Vite, inline styles (no CSS framework), Lucide icons, DM Sans + Manrope fonts
- **Backend:** Node.js + Express, Prisma ORM, PostgreSQL
- **Auth:** JWT (8h expiry), stored in localStorage (`gem_auth`), daily re-login enforced via `loginDate` stamp
- **Hosting:** Vercel (frontend), Railway (backend + Postgres)
- **Git:** GitHub — `marvin28-dev/GymMS-GEM`, main branch

## Key API Endpoints

- `POST /api/auth/register` — create gym + owner (general_manager). Returns `{ token, accessCode, user }`.
- `POST /api/auth/login` — login with gymCode + email + password
- `GET /api/auth/check-code/:code` — check if a gym code is available (no auth)
- `GET /api/auth/me` — current user info
- `POST /api/auth/verify-manager` — verify manager password for sensitive actions
- `GET/POST/PATCH/DELETE` — `/api/members`, `/api/staff`, `/api/packages`, `/api/payments`, `/api/expenses`, `/api/tasks`, `/api/equipment`, `/api/timecards`, `/api/calendar`, `/api/communications`, `/api/notifications`
- `GET/PATCH /api/gyms/me` — gym settings
- `GET /api/staff/:id/code` — reveal staff access code (manager role only)
- `POST /api/attendance/checkin` — check in by accessCode or memberId

## Authentication & Security

- JWT stored in `localStorage` under `gem_auth` with a `loginDate` stamp
- **Daily re-login:** `checkDailyExpiry()` runs at the top of `AppRoutes` — if `loginDate !== today`, auth is cleared before any route renders.
- **Expired token:** `isAuthed()` also reads the `exp` claim out of the JWT itself. The date stamp alone is not enough: signing in at 09:00 and returning to the same computer after 17:00 leaves a same-day stamp on a token that expired, which drew the dashboard and then snapped to the login page on the first 401. Both checks are synchronous, before anything renders, so there is no flash.
- **Logging out clears the gym's details too** (`clearAuth`): country, currency and settings left behind would show the next person to sign in on that browser the last gym's figures.
- **Signing in counts as activity** (`setAuth` stamps `gem_last_activity`). Typing on the sign-in page is not counted (nobody is signed in yet), so a sign-in page left open over 15 minutes used to land a new account on "Are you still there?" seconds after it chose its password (seen in Firefox, which keeps and restores tabs). The warning itself is translated (`idle.*`).
- **Inactivity timeout:** 15 minutes. `useInactivityLogout` hook in `App.jsx` polls every 10s. When inactive: shows a 30-second countdown warning modal ("Are you still there?") before auto-logout. Activity tracking pauses while warning is visible.
- **Manager PIN:** `ManagerAuthModal` component gates sensitive actions (deactivate staff, reactivate staff, view access codes, change salary). Staff reactivation requires manager PIN and makes an API call to `updateStaff(id, { isActive: true })`.
- **Staff access codes:** 4-digit codes auto-generated on creation. Used for front desk login and manager authorization. Revealed on StaffProfilePage behind PIN gate, auto-hides after 30s. "New code" only appears once the current code has been revealed — you cannot replace a code you have not looked at.
- **Signing in asks for the email first.** `POST /api/auth/login-status` answers `existing`, `new` or `unknown`, and the form then shows a password box, a create-password box with the 4-digit code, or says no account uses that address. The lookup is rate-limited per caller (30 per 10 min) because it reveals which addresses belong to the gym. A deactivated account answers `unknown`. **The email is matched without regard to capitals or surrounding spaces** (`mode: 'insensitive'` in every sign-in lookup: login, login-status, set-password, forgot-password).

## Frontend Architecture

### Routing (AppRoutes.jsx)
- Public routes: `/` (landing), `/signup`, `/login`, `/:gymCode/login`
- Protected routes wrapped in `<ProtectedRoute>`:
  - Full-screen: `/front-desk`, `/front-desk/mode`, `/front-desk/member/:id`
  - App layout (sidebar + header): all `appRoutes` from `routeConfig.jsx`

### Key Components
- `DemoTour.jsx` — Interactive system tour with SVG mask spotlight, smooth CSS geometry transitions, auto-positioning cards. 19 steps covering dashboard, members, attendance, calendar, front desk (8 steps with FD tab switching), payments, reports, tasks, packages, staff. Tour triggers for demo mode users AND first-time real users (`gem_tour_seen` flag). Floating replay button visible to all users.
- `AppLayout.jsx` — Sidebar (260px fixed) + Header + `<Outlet>`
- `ProtectedRoute.jsx` — checks `checkDailyExpiry()` then `isAuthed()`
- `ManagerAuthModal` — PIN verification modal for sensitive actions

### Patterns
- Inline styles throughout (no className-based CSS)
- `GemInput` / `GemSelect` — styled form components
- `useLanguage()` context for EN/FR translations
- Money formatting: always `formatMoney()` from `utils/currency.js`. It reads the gym's currency off the session (`user.gymCurrency`), never from browser storage, so every account in a gym sees the same money. Never hard-code a symbol.
- **Everything that names money uses the gym's currency, labels included: never "FCFA", "XAF" or "CFA" in a translation, a label, a placeholder, an email or a PDF.** A label that names the currency takes a `{currency}` placeholder filled with `getCurrencySymbol()` (`memberProfile.amountIn` "Amount ({currency}) *", `memberProfile.amountInShort`, `staff.monthlySalary`). On the server, amounts go through `utils/money.js formatMoney(amount, code)` (each currency's own style: ₦15,000, 15 000 FCFA) and a gym's code comes from `currencyOf(gym)` (its own currency, else its country's); the payment receipt email and its PDF both use it, and the PDF swaps a sign its font can't draw (₦) for the code (NGN 15,000). A new gym whose sign-up sends no currency is given its country's (`currencyForCountry` in `auth.controller register`). The only places a currency is written out are the tables that map them (`utils/currency.js`, `utils/countries.js`, server `utils/money.js`).
- Phone placeholders and address examples come from the gym's country (`utils/countries.js`)
- Gold accent color: `#c9a96e` / `var(--accent-gold)`
- Two themes only: dark (default) and light. Both are defined as tokens in `src/index.css`; components read `var(--...)` and never hard-code a surface colour, or they stay dark in light mode. The light theme is warm stone: the page sits a clear step below the cards so the screen has depth instead of being one bright field.
- **Never load a screen with a bare `Promise.all` over several endpoints** — use `softAll()` from `utils/loadAll.js`. Roles differ in what they may read, so one 403 rejects the lot and the page renders empty; this blanked both Accounting and Daily Overview.
- A shift or event that ends at or before it starts crosses midnight. `components/NextDayHint.jsx` says so under the end-time field, and the server rolls the check-out forward a day (`endOfShift` in the timecard controller) instead of refusing it.
- Putting staff on a gym calendar event raises a task for each of them and notifies them. A private diary entry raises nothing. That task is calendar-flavoured (`category: 'Calendar'`, `eventId` set) and can only ever be `Pending`/`Accepted`/`Declined` — never the ordinary `In Progress`/`Done` — enforced server-side in `task.controller.js`. The invites (one task and one notification per person per date, two `createMany` writes in `tellTheAssigned`) are written before the booking is answered: written afterwards, the live refresh that follows a write showed the event on the invitee's calendar as already accepted, since no invite yet said otherwise. Until they answer, the event is already on that person's own calendar (`GET /api/calendar?mine=1` returns it with `myResponse: 'pending'`), drawn dashed with an "Awaiting your answer" pill, and its details offer Accept / Decline; accepting keeps it there as an ordinary entry, declining takes it off. The event stays on the gym calendar either way, and whoever booked it sees everyone's answer as response chips on the event.
- A task is given to one person, to everyone who does a job (`assignedRole`), or to a whole department (`assignedGroup`, currently only `management` = owner + managers). `gem-frontend/src/utils/departments.js` encodes all three into one form value (`role:trainer`, `group:management`, or a staff id) and `components/TaskAssigneeField.jsx` is the department-first picker every task form uses (Tasks, Dashboard, Operations, Front Desk) — pick a department, then either everyone in it or one person there. Every task form requires an assignee and a due date; there is no Notes field.
- **Changing an ordinary task's status is management's alone** (`general_manager`/`manager`) — not the assignee, not a department member, not even the person who raised it. Enforced server-side in `task.controller.js update()` and gated in the UI (`canCompleteTask` on TasksPage, `canUpdateTasks` on StaffProfilePage). The one exception is a calendar-invite task, whose accept/decline stays the invited person's alone. The status control is the same **three-way toggle (Not started / In Progress / Done)** everywhere it appears — the Tasks page Task-Details modal and the staff-profile Tasks modal both render it (management only; "Done" opens a completion-note step) — and it is **task-kind aware**: a calendar-invite task (`eventId` set or `category === 'Calendar'`) shows **Accept / Decline** instead, and only to the invited person (self). The Tasks-page row still opens via its eye; the Task-Details modal shows Assigned To. A staff profile's **Tasks** tab defaults to what's assigned to them (role/department included, no separate "group" filter) and shows a red count badge of their open tasks; every system-raised task (equipment fault, time-card review, calendar invite) carries a due date. A staff profile's **Calendar** tab shows only upcoming items (no past agenda).
- **Local-day date helpers live in `utils/date.js`: `todayStr()` and `dayStr(d)`.** A "today" comparison must use these, never `new Date().toISOString().slice(0,10)` (the UTC day), which read a day ahead east of GMT and made the calendar highlight the wrong cell and split "upcoming vs past" on the wrong boundary.
- Front desk now has its own calendar (private diary + gym events they've accepted) and can raise real tasks with the same department picker — both were previously missing from the front-desk kiosk (`FrontDeskPage.jsx`), which used to fake task creation locally instead of calling the API.
- **Viewing a colleague's profile is open to everyone; their pay and private notes are not.** `GET /api/staff/:id` used to 403 for anyone who wasn't management outranking the subject — which meant a front-desk (or trainer) clicking "View Profile" on a peer always failed, regardless of routing. `canView` (`gem-backend/src/utils/hierarchy.js`, mirrored in `gem-frontend/src/utils/hierarchy.js`) now always allows opening the page; a separate `canSeePrivateFields(actor, target)` (self, or outranks) gates `salary`/`staffNotes`/`payDay`/`emergencyContact`/`emergencyPhone` in the response, and `StaffProfilePage.jsx` hides the Pay & Earnings and Notes tabs entirely when that's false rather than rendering them empty.
- **`/front-desk/my-profile`** is the front desk's own profile, in the same no-sidebar route group as `/front-desk/staff/:id` — the header's "My Profile" button used to send everyone to `/my-profile`, which lives under the normal `AppLayout` and dropped the person on shift onto the full dashboard shell. `StaffProfilePage.jsx` renders it with no `:id` param (falls back to the signed-in user), and its "Back" button — previously hidden whenever you were viewing your own record, since `/my-profile` never needed one — now also shows whenever `location.pathname` starts with `/front-desk`, so there's still a way back to the desk.
- The full-screen front desk has no app header, so it carries `components/NotificationBell.jsx` — otherwise nothing in the system can reach whoever is standing at it. Profiles opened from the desk use `/front-desk/staff/:id` and `/front-desk/member/:id` so the person on shift is never dropped onto the dashboard.
- **Clear all clears your own list, never the gym's.** The desk's bell, the header dropdown and the Notifications page all have it (`DELETE /api/notifications/all`), and deleting one works the same way: a notification addressed to you (`staffId`) is deleted, a gym-wide one only gets a `NotificationDismissal` row for you (`@@unique([notificationId, staffId])`, cascades with the notification), so everyone else still sees it. `visibilityWhere` (`utils/notificationScope.js`) leaves out what you dismissed. Its "nobody hears about themselves" rule is written `aboutStaffId: null OR aboutStaffId <> me`: a bare `NOT { aboutStaffId: me }` is unknown, not true, in SQL when the notice is about nobody, and it hid every New Member Joined, New Visitor Registered and Payment Received notice from everyone.
- **A part-time front desk employee's shift is asked about, never assumed.** Signing in and opening the desk with their code no longer clock them in (`autoClockIn` is only reached through `POST /api/timecards/shift/start`). The desk (`FrontDeskPage.jsx`) asks "Check in for your shift?" once per sign-in (`GET /api/timecards/shift?staffId` → `{ clockable, state: none / in / done }`), and after the EOD report is printed asks "Check out now?" for whoever is still on the clock (then `POST /api/timecards/end-of-day`). Both have **Not now**; they can still clock in or out later from the desk's check-in by searching their name.
- **Every time is picked with `components/ui/TimeInput.jsx`, never `<input type="time">`**, and it is kept deliberately simple (the user found a grid picker with hours, minutes and arrows too complicated): a field like any other (clock icon, the time, a down arrow) whose click drops down one list of times every 15 minutes (`step`), scrolled to the chosen one (or the current hour), the chosen one ticked in gold; one click picks and closes. An exact time can be typed on a computer (10:31, 1031, 10.31, 9.5; nonsense is ignored); on a touch screen the field is read-only so the keyboard never covers the list. The list portals to `<body>`, opens above the field when there is no room below, and Escape closes it, not the dialog behind it. It calls `onChange({ target: { value: 'HH:MM' } })` like an input, and `GemInput type="time"` renders it, so forms keep their label and error. Tests drive it through `[data-time-input]` (value in `data-value`) and `[data-time-panel] [data-time-option="HH:MM"]`.
- A list that starts empty flashes its "nothing here yet" message before the data lands, which reads as flicker. Pages with a list keep a `loading` flag and render `components/Skeleton.jsx` while it is true.
- **A skeleton alone is not enough for a list you revisit.** A fixed-size skeleton (say 5 rows) that then collapses to the real, often shorter, list is itself a jump. List pages seed their state from `utils/gymCache.js` (`gymCache('<page>')` → `read`/`write`/`has`, scoped per gym): a page that has been open before renders its last data at once and the fetch only swaps in changes, so `loading` is only true on a first-ever visit. Applied to Staff, Members, Tasks, Payments, Attendance, Sales, Communication, Accounting, Operations, TimeCards, Packages; Dashboard and Front Desk did the same by hand before this helper existed.
- The `.page-fade` entrance (`src/index.css`) slides an already-opaque page up a few pixels — it deliberately does NOT fade from `opacity:0`. Fading from transparent left one frame where the just-mounted page was invisible and the dark background showed through, which read as a black flicker on every navigation.
- **Payroll settles on the server.** `PATCH /api/payroll/:id/status` with `paid` books the salary expense (category Salaries, paid by the method chosen in the settle dialog) and links it (`PayRecord.expenseId`) in one transaction; `issued` takes it out again. `PATCH /api/payroll/:id` (owner; the owner's code in the UI) saves a paystub's allowances and deduction lines and moves a paid pay's expense with it. A linked salary expense can't have its amount changed or be deleted on its own (409). Receipt photos are uploaded to `gem/receipts` and kept on `Expense.receipt`; `PUT /api/expenses/:id/receipt` fills a missing one (management). The old browser-only copies (`gem_paystub_expense_map`, `gem_expense_receipt_<id>`) are handed to the server once by `handOverBrowserRecords` in `AccountingPage.jsx`.
- **The desk may remove only its own payment from the last 15 minutes**; anything older or anyone else's is management's (`payment.controller remove`). **Only management dates a payment on an earlier day** (the Payments page date, up to 90 days back, sent as `paidOn` with `tz` and kept at local midday); everyone else's is dated now.
- Expenses are changed from the detail view, never from a row: the row's 3-dot menu offers View (and Mark reviewed where due), and Edit and Delete inside the detail view are confirmed with the owner's 4-digit code.
- **Every list row's actions live in one 3-dot menu: `components/ui/RowMenu.jsx`** (`items: [{ label, icon, onClick, danger, hidden }]`), even a single action. No inline eye/pencil/trash icons. It portals to `<body>` with fixed positioning (a table's overflow can't clip it), follows its button when anything scrolls, and closes on Escape, an outside click, or once the button leaves the screen. Read the button's position in the click handler, never inside a state updater (the event's currentTarget is null there). Wide tables pin their Actions column with `position: sticky; right: 0` so the menu stays reachable when the table scrolls sideways (see `stickyActions` in `MembersPage.jsx`). The pinned column's edge shadow is drawn only while rows actually pass under it (`pinnedEdge`, measured from the scroll box): Firefox paints a cell's shadow on every row, which left a dark stripe down a table that fits. The pinned header cell paints the header's own wash over the card colour, so it doesn't read darker than its neighbours. A menu with a labelled trigger instead of the dots passes `buttonContent` and `buttonStyle` (the coach dashboard's **Log** menu).
- **"Expiring soon" is one rule, `membershipEndsThisWeek(m)` in `utils/attention.js`**: a non-visitor whose active membership ends within the next 7 days. The Dashboard card, the Members header line and "Expiring Soon" chip, and Daily Overview all use it. The Members header line ("N total · N active · N expiring soon", `members.summaryLine`) counts active with the Active tab's own rule (`filterByTab`), so a visitor with passes counts; it once counted only `status === 'active'` and read "0 active" beside "Active 3".

## Backend Conventions

- All DB queries scoped by `gymId` from JWT
- Member IDs use `GEM-XXXX` format (`memberCode`)
- Prices are integer FCFA (no floats)
- Staff `role` enum: `general_manager`, `manager`, `front_desk`, `trainer`, `other` (`accountant`, `coach`, `instructor` remain only so older records still read; new accounts are never given them, and coach/instructor are treated as trainer everywhere)
- A role decides what someone may open, in code: `gem-frontend/src/utils/rolePages.js` (pages) and `gem-backend/src/middleware/access.js` (API). There is no per-staff permission picker. ("Department" as a page-access concept doesn't exist — only the task-assignment sense in `utils/departments.js` does, see Patterns above.)
- Emergency contact fields stored via raw SQL (`$executeRawUnsafe`) to handle stale Prisma clients
- Notifications created on: new member signup, payment received, new staff added, staff activated/deactivated
- A gym-wide notification that is about one employee carries `aboutStaffId`. Nobody is shown a notice about themselves; a notice addressed to them (`staffId`) still reaches them.
- **Gym settings live on the `Gym` record, never in `localStorage`.** `Gym.currency`, `Gym.country`, `Gym.city` and `Gym.settings` (payment methods, tax, late fee, notification preferences, front desk expense limit) are the only authority. The frontend reads them through `hooks/useGymSettings.js` and the session. Anything put in browser storage differs per account and per device — that is the bug it was moved away from.
- Changing the gym's country in Settings moves its currency with it (`utils/money.js` → `currencyForCountry`), unless a currency is named in the same request.
- The books read the same for everyone, wages and names included. Who may change an entry is settled on the write routes, not by hiding rows: only the general manager may PATCH or DELETE an expense.
- New staff get a welcome email (`utils/welcomeEmail.js`) with the gym code and how to sign in — never their 4-digit code. Switched off by the gym's `settings.notifications.welcomeEmail`.
- Only management may create a non-private calendar event — enforced in `calendar.controller.js create()` by deciding `isPrivate` from the caller's role, never trusting a client-sent `isPrivate: false`. A trainer or front desk staff can only ever add to their own diary.
- Reporting an equipment issue (`POST /api/equipment`) also raises a management maintenance task and notifies the managers — `raiseIssueTask()` in `equipment.controller.js`, best-effort so the issue still saves if the task fails. Severity maps to task priority (critical→high).
- **Leaving front-desk mode for the app always goes through one gate — the manager's own account _password_** (not the 4-digit PIN; this is the one approval that asks for the password, decided deliberately for exiting the kiosk). In `FrontDeskPage.jsx`, `requestExit(target)` is the single door: the Exit button and a notification that deep-links into the app both call it, and `handleExitConfirm` verifies the password via `verifyManagerPassword(...)` (→ `POST /api/auth/verify-manager` `{authorized}`) before navigating. There is **no profile picker** — the exit modal is a single password field. The glimpse of the kiosk login/picker on the way out is gone because the exit no longer flips `session` to null before navigating (it only clears `sessionStorage` and navigates, so the page unmounts straight away). A real `front_desk`-role account has no dashboard to protect, so its notifications open directly — but through `toKioskLink()`, which rewrites any app-shell deep-link to its no-sidebar kiosk twin (`/my-profile`→`/front-desk/my-profile`, `/staff/:id`→`/front-desk/staff/:id`, `/members/:id`→`/front-desk/member/:id`, and any `/tasks` → the person's own kiosk tasks tab). To that end a task-assignment notification points the **assignee** at the role-agnostic `/my-profile?tab=tasks` (set in `task.controller.js create()`), never `/staff/:id?tab=tasks` which front desk cannot open; only the creator's own confirmation keeps the `/staff/:id` link.
- **Every front-desk expense is sent for a manager's _review_, and anything over the gym's `settings.expenseLimit` can't be created at all.** The word is **review, not approval** — the money is already spent, the manager is only checking the entry. `expense.controller.js create()` decides from the caller (`source: 'frontdesk'` or a `front_desk` role): over the limit → **400, blocked** (a manager must record it directly); within the limit → `approvalStatus: 'pending'` (user-facing: "awaiting review") and every manager is notified ("Expense needs review"). An expense booked by management directly (no `source`) goes straight in as `approved`. **`paidTo` is required on every expense create** — server-side (400 "Paid to is required") and in both forms (front-desk kiosk and Accounting). `getAll` returns only non-pending by default (so finances exclude pending), and `?pending=1` returns the waiting ones. `PATCH /api/expenses/:id/approve` (MANAGEMENT only; internal name is still `approve`) moves one into the books and notifies the submitter ("Expense reviewed"). The Accounting overview shows an "Expenses awaiting review" panel (GM/manager) with a **Mark reviewed** button per row. The front-desk form's submit reads "Send for review". Once reviewed, an expense is an ordinary booked row — the All/Operations expense table shows only a view (eye), never a stray Approve/Reject on an already-reviewed entry.
- **A member can check in many times a day, but not twice within 30 minutes, whoever they are and however they pay** (visitors and day passes included, so a pass is never spent twice for one visit). `attendance.controller checkIn()` looks for a member check-in in the last 30 min before recording; if found it returns **409 `{ alreadyCheckedIn: true }`** and records nothing (no pass spent). The 409 carries `lastCheckIn`, and every check-in button shows the same message through `utils/checkin.js checkInErrorText` ("X already checked in at 10:15. The next check-in is possible from 10:45."), never a fake "Check-in confirmed"; the hero's Check In button flashes "✓ Check-in confirmed" — just the text's tick, no extra icon (the icon-plus-text was the double-checkmark bug).
- **Day passes have their own counter, `Member.dayPasses`, apart from `passesRemaining`** (a package's session limit, or a visitor's bundle passes). Mixing them once let a frozen member on a limited package in on leftover sessions, and left an active member who had used day passes stuck at "no sessions". The check-in rule (server `attendance.controller checkIn()`, mirrored in `utils/checkin.js checkInBlockReason`): a **visitor** (`isVisitor`, whatever the status) spends a bundle pass while the bundle is within its `endDate`, then a day pass, else 403; a **lapsed** member (`frozen`/`suspended`/`expired`/`cancelled`/`deactivated`) gets in only on a day pass; anyone else on their membership, with `passesRemaining` as a session limit when set. A visitor with nothing left flips to `expired` but keeps `isVisitor`, so screens decide "visitor" from the flag, never the status. Every visit records how it was paid for in `Attendance.kind` (`day_pass`, `visitor_pass`, or null for a membership); `components/ui/VisitKindBadge.jsx` shows it in every check-in list. A visitor bundle's `durationDays` sets the visitor's `endDate`. `pending` also 403s. The front-desk check-in paths (`handleCheckIn`, `handleCodeVerifyCheckIn`) and the **attendance page's member result card** surface the server error (`staffClockError`/`codeError`/`checkInError`) instead of swallowing it and faking "checked in"; the attendance page's "no photo ⇒ enter code" rule is **off on the dashboard** (management is trusted) — it stays a front-desk kiosk measure.
- **A package carries a `dayPassPrice` (required when creating a monthly/non-visitor package).** A lapsed member's day pass is priced from their own package's `dayPassPrice` (a single day, no quantity); a visitor tops up passes on the visitor package. `DayPassModal`, `ConvertToVisitorModal` and `ConvertToMemberModal` take payment up front (never offset by debt) and persist via `updateMember`. Convert-to-visitor picks a **visitor bundle** (its session count comes from the package — no quantity picker) and charges the standard price; convert-to-member goes through the renew/choose-membership flow (valid statuses only — `registered`/`cancelled` are NOT in the `MemberStatus` enum).
- **A visitor's pass count is bundle passes plus day passes, shown as one number everywhere** via `passesLeft(m)` / `passesOf(m)` in `utils/checkin.js` (profile, front desk, attendance, members check-in). Buying a visitor a day pass adds one to `passesTotal` and `dayPasses` and stretches `endDate` to at least today; a day-pass visitor's `endDate` is the day it was bought. An end date is the last day passes work, compared by calendar day.
- **Nobody is added without the money collected first** (`components/CollectPaymentStep.jsx` in both Add forms; Create stays locked until it is done). A new member's registration fee (when the gym charges one) and a new visitor's bundle or day pass are taken in the form, and the server refuses `POST /api/members` without them (`regFeeMethod` for a member, `initialPayment` for a visitor). A visitor's first payment is written in the same request as the visitor, so neither exists without the other.

Their own profile says "Your manager adds it once they have checked your ID" instead of an Upload button, on desktop and phone. The file picker is rendered once at the top of both layouts so the profile checklist's Photo ID opens it from any tab and on a phone (it used to do nothing on a phone), and a failed upload shows its error.
- **The calendar is one set of Month / Week / Day views for every tab, phone and desktop** (`CalendarPage.jsx`, rebuilt): clicking a day box, a week column or a day-view hour opens the add form on that day (and hour), but for a coach or the desk only on **My Calendar** (`canAddHere`): their Gym Calendar has no add button and its boxes only show what is on; past days and hours are not clickable, and the server refuses booking into the past (`inThePast` in `calendar.controller.js`, from the browser's `tz`). A coach's or the desk's **Gym Calendar** shows only the gym's (non-private) events; **My Calendar** shows their own entries, accepted gym events and their open tasks (on their due date), plus events they were put on and have not answered yet (dashed, see the calendar-invite rule above), with the pending invites also listed above. **A month day box shows only its first entry, then "+N more"** (`calendar.plusMore`, `data-more`), which opens that day; this holds on every tab. A coach's add form offers **Train a client** (pick from their own active clients; the event is `category: 'Training'` with `memberId`, titled "Training: Name") or **Personal**. On phones the month is a compact grid with the tapped day's list and an "Add on" button below. The add form used to sit inside the gym-only part of the page, so "Add to my calendar" did nothing on My Calendar.

In the calendar form it appears only once both a start and an end time are set, and only for an entry that overlaps that time range (a coach overlapping their own entries; a manager putting staff on an event); something else on the same day is not a warning there and in every task form when the task goes to one person (`TaskAssigneeField` with `dueDate`: everything they have that day, since tasks have no time). Someone else's private entry reads "a personal entry" or "training a client", never its title.
- **Addresses are the same on every form** (`utils/address.js`, `components/AddressInputs.jsx` for staff and the member profile edit, `AddressFields` in `MembersPage.jsx` for the Add Member / Add Visitor forms): house number, street, city, region, postal code, country. Street, city and region are required (`*`), and city and region suggest the country's names. **The country is always the gym's own and cannot be changed**: forms show it read-only with a lock (`CountryField` in `AddressInputs.jsx`, used by `AddressFields` too), and the server sets it from the gym on every member and staff create and edit, whatever is sent. Members and staff both store `city`, `region`, `country` (staff gained the whole address), and the server refuses a new member or staff member without city and region. Profiles show it on one line (`formatAddress`).
- **The staff list matches the Members page**: Active / Deactivated tabs with counts inside the card (general manager only), the email under the name, the role as a coloured chip (same colours as the phone cards), and a "Showing N staff" footer. It has **no search box** (the user did not want one; a gym's staff fits on one screen).
- **A form's errors go under the field that caused them, never in one box at the bottom.** Every form sets an error per field and renders it under that field (`GemInput`/`GemSelect` `error` prop, or a line in `fieldErrorStyle` from `utils/formErrors.js`). The server names the field in its refusals (`{ error, field }`, e.g. staff/member create and edit, coach goals and progress, calendar `inThePast`), and `serverFieldError(err, fallback)` turns that into `errors[field]`; only a refusal without a field is shown for the whole form. Error lines carry `role="alert"` and `data-field-error`, and `revealFirstError()` scrolls the first one into view after a refused save (on a long form the Save button sits far below the fields).
- **The shared `Modal` is a real dialog** (`role="dialog"`, `aria-modal`, labelled by its title; the close button is labelled).
- **The member profile's tab row scrolls on its own** (`overflowX: auto`): wider than a phone, it used to slide the whole page sideways when a tab near the edge was tapped.
- **`StaffProfilePage` uses the same hero concept as the member profile**: one card with the identity band (photo + name + status + role badge + phone/email), and a key-stat strip (department / employment / join date), with Send login link, Deactivate-Reactivate and the **✕ Close** button (was "← Back to Staff/Front Desk") together on the name line (Edit lives on the Staff Details heading) — shown only when not viewing your own profile, or in the kiosk, and still calling `backToList()`.
- **On a desk-sized screen the front desk is held to the window** (`height: 100vh`, body grid `gridTemplateRows: minmax(0, 1fr)`), so each column scrolls on its own: a long recent check-ins list, product grid, sales list or cart never drags the whole page, and the keypad, headers and Record Sale stay in place. Phones stack the columns and scroll as a page, with the sales list capped at half the screen.
- The front-desk body grid is `260px minmax(0, 1fr) 300px` — the centre uses `minmax(0, 1fr)`, not `1fr`, so wide/unshrinkable profile content (tables, etc.) can't push the centre column past its share and shift the layout when a profile opens over the keypad.
- **The desk can re-send a member their check-in code** — **Email it / Text it** on the `MemberDrawer`, on the member profile's **Send check-in code** action (`SendCodeModal`), and as the "forgot code?" fallback in the desk code-entry modal. It is NOT on the search-result card. Email is real: `POST /api/members/:id/send-code` (`only(DESK)`) → `sendAccessCode()` in `memberEmail.js`; the controller wraps the send so a provider refusal returns a clean 502, not a 500. Text has no SMS gateway, so it opens the device's own messaging app via an `sms:` link prefilled with the code. The shared helpers `emailCodeToMember(m)/textCodeToMember(m)` take the member and return `{ok,text}`. (`SendCodeModal` used to be a fake that just flipped to "sent".)
- **A member's notes live on the server** (`MemberNote`: author, category General/Health/Financial/Other, text, date; `GET/POST /api/members/:id/notes`, desk and management only, `memberNote.controller.js`). Coaches have no Notes tab (their notes are on Progress). Notes a browser kept before (`gem_member_notes_<id>`) are posted to `/notes/import` the first time that browser opens the profile, then removed; sign-out leaves them so they can still be handed over.
- **A member's profile photo can be removed, not only replaced** — the photo modal on `MemberProfilePage.jsx` has a **Remove photo** button (`updateMember(id, { photo: null })`) beside Upload New Photo.
- **A membership start date can't be before today** — `min` on the date input plus submit validation in the Add-Member form (`members.startDateNotPast`) and the renew modal. Editing an existing member is not constrained (historical records).
- **Renewing requires the outstanding balance to be settled first.** `RenewMembershipModal` blocks when `member.balance > 0` and offers **Settle balance** (opens Add Payment); otherwise the old debt would be silently wiped, since `commitRenewal` sets the new balance to `price − paidNow`. Renewal start date is also `min`-guarded to today.
- **The front desk never sees a member's check-in code** — the reveal eye on `MemberProfilePage` is hidden when `fromFrontDesk` or the role is `front_desk` (`canViewCode`). They can still Email/Text it (send without seeing).
- **Member actions that need a manager's sign-off go through an approval engine, applied server-side.** The old on-the-spot manager-code prompt (`ManagerAuthSection`, now unused) is replaced by `ActionConfirm`: a **manager/GM applies the change directly** (`POST /api/approvals/apply`, MANAGEMENT); **anyone else writes a required note and it becomes an approval request** (`POST /api/approvals`, DESK) — a managers' task + notification, and a **Pending approval requests** panel on the member profile where a manager **Approve**/**Decline**s. Approving applies the change from the stored action+params (`POST /api/approvals/:id/approve`) and notifies the requester. One backend place (`approval.controller.js` `ACTIONS` map) decides what each action does, used by both the direct and the approved path; it also made the previously-mock Extend/Freeze/Unfreeze/Convert actually persist. Actions covered: `extend_membership`, `freeze_membership`, `unfreeze_membership`, `cancel_membership`, `convert_to_visitor`. Backed by a standalone `ApprovalRequest` model (no relations). **Whoever sent a request can cancel it while it waits** (`POST /api/approvals/:id/cancel`, sender or management; status `cancelled`, the managers' task is deleted), from the member's Pending approval panel or from the "already waiting" message, which then shows the note box. **A manager working the front desk confirms these actions with their own 4-digit code** (`ManagerAuthModal` in `ActionConfirm` whenever the path starts with `/front-desk`); in the office they apply at once. **A member can have only one request waiting at a time**: `approval.controller create()` checks and writes in one serializable transaction and answers 409 (with the waiting request) otherwise, including when two desks send at the same instant. `ActionConfirm` looks first and shows the waiting request instead of a note box. For the desk the note is a gold "Manager approval needed" panel with the cursor already in it. Actions that take a reason (freeze, cancel) have **one** Reason box (`withReason`, `reasonRequired` for cancel): a manager types the reason; for the desk the reason is the note the manager reads, sent as both `note` and `params.reason`. `GET /api/members` marks each member's waiting request (`pendingApproval`), which puts them under Needs attention (`utils/attention.js`) with an "Awaiting approval" tag on the Members list.

It also did its day maths with `.toISOString().slice(0,10)` (the UTC day), which landed an event a day off east of GMT — now it maps event dates with `dayStr(e.date)` and navigates with `todayStr()`/`dayStr`-based `addDays`/`getWeekDays` (see the local-day rule above).
- A calendar **event** must end after it starts (`calendar.controller` clients validate `endTime > startTime`); only work shifts (time cards) may run past midnight via the `NextDayHint`/`endOfShift` rollover. Task creation everywhere requires a title, an assignee (person/role/department), a due date and a category — there is no free-text "notes" field on tasks.
- The header carries a global search (`components/GlobalSearch.jsx`) over pages and Settings sections, filtered to the role's allowed pages. On desktop it is a **bare 38px search icon** (like the bell beside it) that **expands smoothly in place** into a field on click or Ctrl/⌘K — its right edge is pinned, so it grows leftward into empty header space and never nudges the bell/avatar, with a dropdown directly beneath it (not a centred overlay). On mobile it stays an icon button that opens a centred overlay.
- **Sidebar nav badges count what _needs attention_, not totals** (`components/Sidebar.jsx` via `utils/attention.js`). `memberNeedsAttention` is **payment-timeline only**: the member owes money AND any one of — (0) the membership has started (start date on or before today) and not a franc of it has been paid, so a brand-new unpaid member is chased from day one with no grace; (1) the membership ends within two weeks (or is past); (2) they are more than a week past their start date and have paid less than half the membership (needs `package.price`, which `member.controller getAll` now selects). A future-dated (pending) membership does not flag until it starts. Status alone (expiring/suspended/etc.) no longer flags attention. `taskNeedsAttention` = not settled and either Pending or past its due date. The badge is amber with a dot and hidden at zero. Both Members and Tasks pages carry a matching **"Needs attention"** filter (a toggle on Members, a status chip on Tasks) using the same helpers.
- **An email identifies one person _per kind_, not across kinds** (`utils/emailGuard.js` `findEmailConflict(gymId, email, { scope })`). The same person can be both a staff member and a member (they train where they work), so the same email is allowed across the two tables; it is only blocked against a second staff account (`scope: 'staff'`) or a second member (`scope: 'member'`). All four callers (member/staff create + update) pass their scope.
- **Staff are never deleted, only deactivated.** `StaffPage.jsx` has no delete. The row's 3-dot menu (`RowMenu`) holds View profile, Edit, and Deactivate/Reactivate; the row itself also opens the profile, and the status-changing items are gated by the manager's code (`ManagerAuthModal`). **Only the general manager** sees the Active/Deactivated tabs, the deactivate/reactivate action, or may change a staff member's active status — enforced in the UI and server-side in `staff.controller.js update()` (a 403 if a non-owner flips `isActive`). Deactivated staff drop off the main roster into a **Deactivated** tab (Active is the default); the count sits on the tab.
- **A new member's registration fee is collected server-side** in `member.controller create()`: when the gym's `registrationFeeRequired` is on and `registrationFee > 0` (and it's not a visitor), it writes a `type: 'registration'` Payment (method from the form's `regFeeMethod`), stamps `regFeeDate`, and emails the receipt — so it always shows in Payments regardless of which form made the member. The Add-Member form no longer creates that payment itself. **Every payment emails the member a receipt** when they have an email (`sendPaymentReceipt` in `payment.controller`/`member.controller`). **Every payment carries a reference** (`generatePaymentRef()` → `TXN-…`) and records `balanceAfter` (0 shows as 0, not blank) — the server-side reg-fee payment sets both too.
- **A membership/registration payment's description is auto-filled, and the staff can edit or clear it** (`utils/paymentDescription.js` `autoPaymentDescription(member, type)` → e.g. "Gold membership — October 2026", "Registration fee — Gold"; product/other stay blank). Wired into the three payment forms: `MemberProfilePage` and `DashboardPage` AddPaymentModals (refills when the type changes, unless the staff typed something custom) and `PaymentsPage` (fills on member select). It is only a default placed in the box, never forced.
- **Figure fields accept digits only** (`utils/number.js` `digitsOnly`, paired with `type="text" inputMode="numeric"`). `type="number"` still lets `e/+/-/.` through, which is why the quick-expense box and others once took letters. Applied to every amount input across Front Desk, Dashboard, Payments, Members, Member Profile and Accounting.
- Money/receipt figures strip the `fr-FR` narrow-no-break separator (U+202F / U+00A0) that rendered as a stray glyph ("5/000"), in `utils/currency.js formatMoney` and the backend `receiptPdf.js` / `memberEmail.js`.
- **The Add-Member form's start date is empty and required** (the staff must pick it), and its address/phone placeholders come from the gym's country (`getAddressPlaceholder()`/`getPhonePlaceholder()`), falling back to neutral text when the gym has no country set. **Editing a package is gated by the manager's 4-digit code** (`ManagerAuthModal` in `PackagesPage.jsx`); creating one is not.

- **An event's assigned staff show wherever it is listed, collapsing to "N people" when too many fit on a line** — the Calendar Day-view row and the front-desk program panel both use this (`calendar.nPeople`), showing up to two names then the count; the event detail modal still lists everyone with their response chips. The staff profile has a **Calendar** tab (`StaffProfilePage.jsx`) showing that person's classes and accepted gym events as a dated agenda, and its **Tasks** tab (was "Tasks Assigned") lists tasks reaching them by person, role, department or authorship, filterable by `kind`.
- **The Reports → Marketing tab filters by when members joined** (`AccountingPage.jsx`, `marketingRange` state): pills for last 7/30/90 days, last year, all time, filtering on `member.createdAt` (falling back to `startDate`). All three marketing views — the summary cards, the source-breakdown bars and the member table — read the scoped list.
