# GEM production-readiness audit: report

Branch `production-audit`, made from `main` at `69cefa8`: 214 commits up to `019525c`, the commit the final test runs used (only documents came after it: this report, the progress log, CLAUDE.md and the testing checklist). Nothing has been pushed and `main` was not touched. The audit ran from 19 to 24 October 2026; on 24 and 25 October the recommended decisions were applied, as the owner asked. `AUDIT_PROGRESS.md` holds the working log (file inventory, journeys, every session and every decision); this report is the summary.

## 1. Verdict

**Ready for gyms once you have done the steps only you can do.** Every problem the audit found that stood in the way of a launch is fixed in the code and covered by a test. What is left is settings, secrets and checks on the live services, which need your accounts, and the checks only a person with real phones, inboxes and a printer can make (section 5). The steps are numbered below; section 6 is the same list to tick off.

What blocked a launch, and how it was settled:

- **The start command re-seeded production on every deploy** (F-001, Critical). Railway now runs `node scripts/migrate.js` before each start and starts the server with `node src/index.js` (`gem-backend/railway.json`); the seed never runs on start and refuses a production database (D-1, D-2).
- **No usable migrations** (F-008). A baseline migration and the audit's changes as migrations; `scripts/migrate.js` recognises a database that was built with `db push`, and refuses one that matches no known state rather than guessing (D-4, D-16, D-18).
- **Time zone** (F-074). The server keeps Cameroon's clock (Africa/Douala) unless `TZ` says otherwise (D-19).
- **The demo** (F-002). Nothing is ever sent for the demo gym, its code is reserved, and its people use example addresses (D-2).
- **Money the desk could change by hand** (F-057, F-108, F-181). Renewals, package changes, day passes, visitor bundles and conversions take their payment and make the change in one server transaction; only management may set a balance, dates or passes directly (D-20, D-28, D-29).
- **Payroll was not saved** (F-116). Paying, editing and reversing a pay are done on the server with the salary expense (D-30).
- **`delete-all.js`** (F-010) is gone (D-5).

Steps only you can do, before the first gym:

1. **Back up the production database, then deploy with the new Railway settings.** The backend service must read `gem-backend/railway.json` (set its root directory to `gem-backend`, or its config path to that file). Before each start it runs `node scripts/migrate.js`, which brings the database up to date and refuses one it does not recognise rather than guessing; it starts the server with `node src/index.js`, checks `/api/health` and gives requests under way 15 seconds to finish. Watch the first deploy's log (TESTING_CHECKLIST 25.11).
2. **Secrets.** Change the password written in `Documents/login.txt` (the file is no longer tracked but is still in git history, D-10), and regenerate the Twilio token pasted into a chat on 19 October (D-7; texting is paused, so nothing uses it yet).
3. **Email.** Verify a sending domain in Resend (its SPF and DKIM records) and set `EMAIL_FROM_ADDRESS`. Until then Resend delivers only to the account's own address, so members get no receipts or codes and new owners no confirmation link (TESTING_CHECKLIST 25.4).
4. **Backend settings on Railway** (names in `gem-backend/.env.example`): `DATABASE_URL`; `JWT_SECRET`, a random string of at least 32 characters; `FRONTEND_URL`, the web app's address; `RESEND_API_KEY` and `EMAIL_FROM_ADDRESS`; `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`. `ALLOWED_ORIGINS` only if another site must call the API, `SMS_PROVIDER` left empty while texting is paused, `TZ` only for a gym outside Cameroon's time zone.
5. **Web app settings on Vercel** (read at build time): `VITE_API_URL`; `VITE_SUPPORT_EMAIL` and `VITE_SUPPORT_WHATSAPP` (no support contact is shown anywhere until they are set); `VITE_PHOTO_HOST` only if photos are not on Cloudinary.
6. **Check a Vercel preview**: the security headers are sent, and photos, the staff ID download and the front desk still work under the content policy (TESTING_CHECKLIST 25.13).
7. **Old logos.** If any gym saved a logo before this branch, run `node scripts/move-logos.js` in `gem-backend` (it lists them), then again with `--apply` (D-51).
8. **Backups and monitoring.** Switch on backups for the Railway Postgres (or a nightly `pg_dump` kept outside Railway) and try one restore; put an uptime check on `https://<backend>/api/health`, which answers 503 when the database cannot be reached.
9. **A privacy notice and terms of service.** GEM keeps names, phone numbers, emails, home addresses, dates of birth, photos, staff ID scans, emergency contacts, body measurements and goals (close to health data) and payments. Say what is kept, why, who sees it, for how long, and how a person asks for a copy or deletion; check the data protection law of each country you sell in, and agree with each gym who is responsible for its members' data.
10. **After the first push**, check that the CI workflow passes on GitHub (TESTING_CHECKLIST 25.14). Nothing has been pushed from here.

What the audit changed, in short:

- **167 of 181 findings fixed** and 11 fixed in part; 1 left on purpose and 1 waiting for you (section 2). Changes to behaviour came with a test that fails without them. Among them are the one Critical and all 19 High ones: stored script injection in print and export windows (F-085), one gym reaching another's records (F-044, F-055), balances lost when two desks take payments at once (F-042), a request applied twice when two managers approve it (F-039), sign-in and code checks with no attempt limit (F-003, F-029, F-030), a calendar entry that hung the server (F-047), and a busy database answering 500 to clock-ins and approval requests (F-176).
- **Tests from none to 74 unit tests, 338 API tests and 290 browser tests** (77 spec files), run in Chromium, Firefox and WebKit at desktop size and on an iPhone and an Android phone profile, covering every user journey (AUDIT_PROGRESS.md section 3a). Email, texts and uploads are fakes, so no message or file leaves the machine.
- **Security**: signing out ends the token on the server (D-3); the web app sends security headers and a content policy (D-45); new owners and changed addresses are confirmed by email (D-8); 8-character passwords (D-36); a colleague's pay and notes stay off the front desk (D-41).
- **For the people using it**: every Settings section works on a phone (D-40); members are written to in English or French, the gym's choice (D-23); phones may zoom (D-49); every text colour reaches 4.5:1 in both themes, checked by axe on every rule (D-48); nothing on the landing page is made up (D-34).
- **Speed**: pages load as they are opened (the first download went from 706 kB to 202 kB compressed), answers are compressed (a 100-member list from 105.7 KB to 4.4 KB), and the sidebar no longer downloads every member on each page change.
- **Running in production**: the server checks its settings at start, its health check asks the database, a deploy lets requests under way finish (D-52), CI runs the lint, unit, API and Chromium and Firefox browser tests on every push (D-12), and known vulnerable packages were upgraded (F-023).

```sh
npm install
npx playwright install chromium firefox webkit
(cd gem-backend && npm install) && (cd gem-frontend && npm install)
npm run test:unit
npm run test:api                          # needs PostgreSQL; uses a database named ..._test
npx playwright test                       # Chromium and Firefox
E2E_BROWSERS=all npx playwright test      # adds WebKit and the phone profiles
```

The API and browser tests make their own database: `TEST_DATABASE_URL` if set, otherwise the server in `gem-backend/.env` with the database renamed `gem_test`.
